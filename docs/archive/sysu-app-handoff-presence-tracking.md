## Overview

The `sysu-go` driver app is getting a **strict session tracking update**. The goal:

- Driver **online / moving** → **GREEN** marker with live GPS updates
- Driver **disconnects / backgrounds / loses network** → Marker turns **RED**, freezes at last known GPS position, **does NOT disappear**
- Driver **reconnects** → Marker turns **GREEN** immediately — no need to wait for movement

The backend (`server.js`) has already been updated. **Sysu-app needs to update how it handles `vendor_status_update` and `update_admin_map` events.**

---

## What Changed on the Backend

The `onlineDriver` Map in `server.js` now stores `{ socketId, name, lat, lng }` for each connected driver:

- `lat`/`lng` are updated on **every** `driver_moving` event received
- When a driver disconnects, the backend emits `vendor_status_update` **with** last known lat/lng:
  ```json
  {
    "driverId": "firebase_uid",
    "name": "Driver Name",
    "status": "offline",
    "lat": 14.599512,
    "lng": 120.921987
  }
  ```
  - If driver sent at least one `driver_moving` before disconnecting → `lat`/`lng` are the last GPS coordinates
  - If driver never moved (e.g. opened app then immediately force-closed) → `lat`/`lng` will be `null`

---

## Socket.IO Events Reference

| Event | Direction | Trigger | Key Payload |
|---|---|---|---|
| `update_status` | driver → server | Socket connect, reconnect, app background, explicit offline | `{driverId, status, name, lat?, lng?}` |
| `vendor_status_update` | server → sysu-app | On every `update_status` received + on disconnect | `{driverId, status, name, lat?, lng?}` |
| `driver_moving` | driver → server | Every ~5s while moving (10m min distance) | `{driverId, lat, lng, sapDocId, name}` |
| `update_admin_map` | server → sysu-app | Forwarded from every `driver_moving` | `{driverId, lat, lng, sapDocId, name}` |

> **Note on `lat`/`lng` in `update_status("online")`:**
> When `update_status("online")` is emitted, the driver app automatically attaches the
> driver's most recent GPS coordinates from SharedPreferences (the same coords persisted
> before every `driver_moving` emit). These represent the driver's **last known trip position**
> — close enough to immediately show the driver on the map. The next `update_admin_map`
> event will update the marker to real-time coordinates.
>
> **`lat`/`lng` = 0 sentinel:** `lat: 0, lng: 0` on `vendor_status_update` means "no position available"
> from the driver app. This is an intentional sentinel value — 0.0 is never a valid GPS reading in
> the Philippines (~4.5°N to 21°N, ~116°E to 127°E). The driver app uses `FusedLocationProviderClient`
> which only produces real satellite/network fixes, never `0.0, 0.0`. Treat `0, null, undefined`
> the same way — use Manila fallback for any of them.
>
> **Edge case — brand new driver with no prior `driver_moving`:** If `lat`/`lng` are `null` or `0`
> in `vendor_status_update {online}`, the driver has no prior trip position in SharedPreferences.
> Sysu-app should either place the GREEN marker at a default/known location and update
> immediately when the first `update_admin_map` arrives, OR show a "locating..." state until
> `update_admin_map` fires with valid coordinates.

## Required Changes in sysu-app

### 1. `vendor_status_update` — `status: "offline"`

**Current behavior:** Remove the driver marker from the map.

**Replace with:**
```js
// vendor_status_update handler
if (status === "offline") {
  if (lat != null && lng != null) {
    // Driver disconnected but we have their last known position.
    // → Turn marker RED and freeze at this position. Do NOT remove.
    upsertDriverMarker(driverId, {
      position: { lat, lng },
      color: "RED",
      label: "OFFLINE"
    });
  } else {
    // Edge case: driver disconnected before sending any driver_moving.
    // (e.g. opened app, immediately force-closed before GPS got a fix)
    // → No position known, safe to remove marker.
    removeDriverMarker(driverId);
  }
}
```

### 2. `vendor_status_update` — `status: "online"`

**Requirement:** When `status: "online"` arrives, turn the marker **GREEN immediately**. Do NOT wait for `update_admin_map`.

```js
if (status === "online") {
  // Turn GREEN right now. update_admin_map will update position next.
  upsertDriverMarker(driverId, {
    position: lastKnownPosition[driverId] ?? /* keep existing */,
    color: "GREEN",
    label: "ONLINE"
  });
}
```

### 3. `update_admin_map` — when driver is currently RED

When a `driver_moving` / `update_admin_map` event arrives for a driver that sysu-app currently shows as RED (offline):

```js
// update_admin_map handler
// If driver is RED, they just reconnected and started emitting driver_moving
// before sysu-app received the vendor_status_update: online.
// → Turn GREEN immediately AND update to the new position in one step.
upsertDriverMarker(driverId, {
  position: { lat, lng },
  color: "GREEN",
  label: "ONLINE"
});
```

### 4. Initial load — already-online drivers on first connect

When sysu-app first loads and connects to the socket, it will receive `vendor_status_update {status: "online"}` for every driver currently in the `onlineDriver` Map. Handle this as a normal `online` event — place GREEN markers at each driver's last known position.

## 🚨 ACTION REQUIRED — WiFi / Network Loss Edge Case

> **This section added 2026-06-06 after discovery during sysu-go Layer 2 fix**

### Problem

When a driver **disables WiFi or loses internet connection** while the app is running in the foreground (not backgrounded, NOT home-pressed — the app is in `TransitActivity` doing active trip tracking):

1. The driver's phone reports `CONNECTIVITY_CHANGE` (network loss) to the OS
2. The Socket.IO socket cannot emit — it's dead
3. The backend only learns the driver is gone after the **30-second ping/pong timeout**
4. Until then, sysu-app still thinks the driver is GREEN on the map
5. After 30s, the server's `disconnect` handler fires → `vendor_status_update {offline}` → sysu-app should turn RED

**Expected behavior:** sysu-go emits `update_status("offline")` **proactively** the moment `CONNECTIVITY_CHANGE` fires (network loss detected), so sysu-app turns RED **within ~1 second**, not 30 seconds later.

### What sysu-go is doing (done ✅)

`sysu-go` now registers a `BroadcastReceiver` for `CONNECTIVITY_ACTION` on both `MainActivity` and `TransitActivity`. On network loss:

```kotlin
// Within BroadcastReceiver.onReceive:
val activeNetwork: NetworkInfo? = connectivityManager.activeNetworkInfo
val isConnected = activeNetwork?.isConnected == true
if (!isConnected) {
    SocketManager.emitOfflineStatus(driverId, driverName)
    showDialog("Walang Internet Connection")
}
```

`emitOfflineStatus()` → `update_status("offline")` with lat/lng auto-attached from SharedPreferences → `vendor_status_update {offline, lat, lng}` on the server → sysu-app.

### What sysu-app Must Handle (ACTION NEEDED)

⚠️ **IMPORTANT:** Even with proactive offline emission from sysu-go, sysu-app should **also** handle the 30-second Socket.IO timeout gracefully. Here's why:

- If the `update_status("offline")` emit fails (socket dead before packet sent), sysu-app falls back to the server `disconnect` event after 30s
- The `vendor_status_update {offline}` from server `disconnect` also carries `lat`/`lng` — sysu-app should turn RED at last known position

So sysu-app needs to handle **both** sources of offline:
1. Direct: `vendor_status_update {status: "offline", lat, lng}` — from sysu-go proactive emit
2. Timeout: `vendor_status_update {status: "offline", lat, lng}` — from server `disconnect` handler after 30s ping timeout

**Both should result in RED marker at last GPS — not removed.**

Additionally, if the driver **reconnects** (network comes back, app stays open in `TransitActivity`), sysu-app must handle `vendor_status_update {status: "online"}` turning the marker GREEN again immediately.

### Verify Fix

1. Open driver app → start active trip in `TransitActivity` → marker is GREEN
2. **Disable WiFi** (or Airplane Mode) on the driver's phone
3. Within ~1-2 seconds: you should see the marker turn **RED** (not disappear)
4. **Re-enable WiFi**: within ~1-2 seconds, marker should turn **GREEN** immediately
5. If it takes 30 seconds to turn red, the proactive emit from sysu-go is NOT arriving — check socket connectivity and server `update_status` handler

### Checklist for sysu-app team

- [ ] `vendor_status_update {status: "offline", lat, lng}` → turn RED at that position (not remove)
- [ ] `vendor_status_update {status: "online"}` → turn GREEN immediately (don't wait for `update_admin_map`)
- [ ] Handle rapid offline→online→offline sequences gracefully (connection blip)
- [ ] Marker must NOT disappear on disconnect — only color change and label update

### `emitOfflineStatus()` — does it ever send lat/lng?

**No. Never.**

```kotlin
// SocketManager.kt — emitOfflineStatus()
fun emitOfflineStatus(driverId: String?, driverName: String) {
    val json = JSONObject().apply {
        put("driverId", uid)
        put("status", "offline")
        put("name", driverName)
        // ❌ NO put("lat", ...) — no lat/lng is ever added
    }
}
```

`emitOfflineStatus()` is called by the `BroadcastReceiver` on WiFi kill **and** by the "End Trip" button. Both paths produce `update_status("offline")` **without** lat/lng.

The `lat/lng` that arrive in `vendor_status_update {offline, lat, lng}` come from the **server's** `onlineDriver` map — specifically from the `disconnect` handler (30s ping timeout) or the `update_status` offline handler (after fix `822b94d`, which preserves coords by reading before deleting).

**Summary of the two offline paths:**

| What fires it | How lat/lng gets in `vendor_status_update` | sysu-app action |
|---|---|---|
| `emitOfflineStatus()` → `update_status("offline")` | Server reads from `onlineDriver` map AFTER fix `822b94d` | **RED** at those coords |
| `emitOfflineStatus()` → `update_status("offline")` (before `822b94d`) | Server deleted before emitting — **lat/lng null** | ❌ Bug — marker removed instead of RED — fixed in `822b94d` |
| Socket.IO `disconnect` (30s timeout) | Server reads `onlineDriver` in `disconnect` handler | **RED** at those coords |

The explicit End Trip scenario arrives to sysu-app as `vendor_status_update {offline}` **without** lat/lng — guaranteed, because `emitOfflineStatus` never puts them in, and the server also has no `onlineDriver` entry to read from by that point (it's deleted). So your "remove" logic is safe.

**There is no scenario where End Trip delivers lat/lng.** The only `vendor_status_update {offline, lat/lng}` you'll ever see is a WiFi kill or ungraceful disconnect — which should be RED, not removed.

## 🔧 Backend Fix — Multi-Socket Tracking (commit `30de32e`)

> **Deployed 2026-06-06** — must be live on Railway before testing.

### Problem

`onlineDriver` stored ONE socket per driver (`socketId: string`). But the sysu-go driver app connects to **two sockets simultaneously** (Railway + sysu-app). When one socket was killed (Ctrl+Shift+R, WiFi flap):
- `disconnect` handler deleted the driver's entry entirely
- Even though another socket was still alive → driver was still ONLINE
- Server emitted `vendor_status_update {offline}` anyway → sysu-app turned driver RED unnecessarily

### Fix

`onlineDriver` now tracks ALL sockets per driver using a `socketIds: Set`:

```js
onlineDriver.set(verifiedUid, {
  name: fullName,
  lat: lat ?? null,
  lng: lng ?? null,
  socketIds: new Set([socket.id])   // ← Set, not single string
});
```

**`disconnect` handler now:**
```js
entry.socketIds.delete(socket.id);
if (entry.socketIds.size === 0) {
  // No sockets left → OFFLINE
  onlineDriver.delete(id);
  io.emit("vendor_status_update", { driverId: id, name: entry.name, status: "offline", lat: entry.lat, lng: entry.lng });
} else {
  // Other socket(s) still alive — driver stays ONLINE
  console.log(`Driver ${entry.name} still online via ${entry.socketIds.size} other socket(s)`);
}
```

**Result:** Driver only goes OFFLINE when ALL sockets are gone. Ctrl+Shift+R on one tab/browser doesn't affect the marker.
